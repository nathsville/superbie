# Lapor Pak Wali

Paket ini adalah fondasi dokumentasi untuk pengembangan **SuperBie – Lapor Pak Wali**, dengan fokus utama pada fitur pengaduan masyarakat. **Perubahan lingkup disetujui (Phase 3, O-1):** selain Lapor Pak Wali, **WINDY — dashboard cuaca publik (baca-saja, tanpa login) pada landing page** kini termasuk lingkup yang disetujui (lihat `_superbie_audit/WINDY_MIGRATION_PLAN.md` dan kelima dokumen spesifikasi terkait). Modul **JDIH** tetap **tidak dibangun** pada fase ini (hanya label navigasi); **tidak ada** GIS/peta batas wilayah. **Perubahan lingkup disetujui (PHASE S, 2026-10-17):** modul **SIPHP** (informasi harga pasar + direktori retail) kini **disetujui** sebagai rebuild native di SuperBie — input manual oleh Super Admin, tampilan publik baca-saja di `/siphp` (keputusan D-S1…D-S7; lihat `SIPHP_INTEGRATION_PLAN.md`). Arsitektur boleh menyiapkan ruang ekspansi; tabel SIPHP wajib ditulis di `schema.md` lebih dulu (§4.12–§4.16) sebelum migrasi dibuat, dan jangan membuat tabel WINDY sebelum gerbang desainnya (F3) terpenuhi dan `schema.md` diperbarui lebih dulu. **Keputusan pemilik WINDY (Phase 4E, D-11…D-17):** horizon prakiraan **3 hari** dari **BMKG gratis** (tanpa penyedia berbayar); tampilan **WITA** (konvensi penyimpanan waktu masih terbuka); ambang lama hanya **nilai awal** (satuan/periode hujan & data gelombang harus diperjelas); **tanpa impor historis Google Sheets**; sinkronisasi **terjadwal + manual** (manual oleh Super Admin; terjadwal bergantung host scheduler yang belum terverifikasi; Admin monitoring-only); patuhi **atribusi** BMKG/OWM; **tanpa** teknologi/Docker baru.

## Isi paket

- `prd.md` — kebutuhan produk, scope MVP, user journey, acceptance criteria.
- `architecture.md` — arsitektur Laravel, alur sistem, keamanan, deployment.
- `schema.md` — sumber utama model data, tabel, relasi, validasi, dan kontrak endpoint.
- `design.md` — design system dan standar animasi UI.
- `rules.md` — aturan implementasi yang wajib diikuti AI coding assistant/developer.
- `PRODUCTION_OPERATIONS.md` — runbook operasi produksi (scheduler, queue, health, backup/restore, monitoring, CI, deployment) dengan status **IMPLEMENTED / REQUIRED / DECISION REQUIRED** (Prompt 23).

Versi dokumen yang telah diperbarui mengikuti perubahan kebutuhan: akun masyarakat/pelapor wajib login, Operator sebagai penangan operasional laporan, Admin hanya monitoring, dan Super Admin memiliki akses penuh. Peran historis `petugas` tidak lagi menjadi active role.

## Cara menggunakan untuk vibe coding

1. Letakkan kelima dokumen ini di root repository.
2. Berikan `rules.md` sebagai instruksi permanen kepada AI coding assistant.
3. Minta AI membaca `prd.md`, `architecture.md`, `schema.md`, dan `design.md` sebelum mengubah kode.
4. Implementasikan per irisan vertikal kecil: setup proyek → autentikasi masyarakat/internal → dashboard masyarakat → formulir pengaduan → riwayat/detail laporan → panel Operator/Admin/Super Admin → pengujian.
5. Setelah setiap tahap, jalankan test dan review diff. Jangan meminta AI membuat seluruh aplikasi dalam satu perubahan besar.
6. Jika kebutuhan belum dipastikan, catat sebagai `TODO: Define requirement`; jangan mengarang aturan layanan publik.

## Keputusan teknologi utama

- Laravel monolith, Blade, Alpine.js, Tailwind CSS, dan MySQL. (Livewire **tidak** dipakai — tidak ada dependensi Livewire; interaktivitas ringan memakai Alpine.js.)
- Navigasi internal **progressive enhancement** (Prompt 26): `resources/js/navigation.js` meng-intercept klik GET internal via `fetch()` lalu menukar region shell (`#main-content`, `#primary-navigation`, `#page-heading`, `#page-actions`) dengan HTML Blade dari server, plus cache in-memory per-tab yang identity-scoped (TTL 60 s, maks 10 entri). Ini **bukan** SPA: tidak ada router/state framework, Service Worker, `localStorage`, atau API baru; Laravel tetap source of truth, mutasi tetap dinavigasi penuh, dan authorization tetap server-side. Jika JavaScript gagal, aplikasi tetap berjalan normal.
- Laravel session authentication untuk masyarakat/pelapor dan seluruh panel internal. Masyarakat/pelapor wajib login sebelum mengirim pengaduan.
- Peta: **Leaflet ^1.9.4 + OpenStreetMap** (tanpa API key) untuk lokasi laporan opsional (Prompt 4/5) dan kartu analitik **Peta Wilayah Aduan** pada Dashboard Admin (Prompt 5/5). Dua dependensi peta tambahan dicatat eksplisit: **`leaflet.markercluster` ^1.5.3** (clustering) dan **`leaflet.heat` ^0.2.0** (heatmap) — di-*bootstrap* via `resources/js/leaflet-global.js` (menyiapkan `window.L` lebih dulu) lalu `resources/js/leaflet-plugins.js`. Peta Dashboard Admin bersifat **read-only**, tanpa batas wilayah/GeoJSON/choropleth, dan **tidak** memakai geolokasi perangkat. Titik peta hanya dibentuk dari pasangan `latitude`+`longitude` yang valid; `location_text` tidak pernah menjadi sumber koordinat. Kartu ini berada di dalam komponen Blade tersendiri (`resources/views/components/dashboard/geographic-map.blade.php`) dan memakai ulang `DashboardCacheService` (TTL 60 s) — **tanpa migrasi/route baru**.
- **Reverse geocoding alamat (penyimpangan scope disetujui pemilik):** PRD semula menempatkan *geocoding* di luar scope dan kontrak peta menjanjikan koordinat "tidak pernah dikirim ke mana pun selain form". Atas persetujuan pemilik, *form warga* (Buat + Edit Laporan) dapat **mengisi otomatis "Lokasi / Alamat Detail" (`location_text`)** dari titik peta/GPS melalui **OSM Nominatim**. Karena ini mengirim koordinat ke **pihak ketiga**, fitur **digated oleh checkbox opt-in eksplisit**: tidak ada permintaan jaringan sebelum warga mencentangnya. Bersifat *saran saja* — field tetap input teks biasa, hanya diisi **bila masih kosong** (alamat manual tak pernah ditimpa), dan server tetap memvalidasi `location_text` sebagai teks opsional (tanpa aturan baru). Konfigurasi `config/map.php` (`MAP_REVERSE_GEOCODE`, `MAP_GEOCODE_URL`, `MAP_GEOCODE_EMAIL`, `MAP_GEOCODE_LOCALE`). Komponen: `locationAddress` di `resources/js/app.js`. Halaman staf/detail tetap **tanpa** reverse geocoding.
- **Geographic Analytics Layer 1 (Prompt 6/5)** — kartu analitik administratif **khusus Dashboard Admin** (read-only), dihitung server-side di `DashboardCacheService` (di dalam cache `dashboard:admin`, TTL 60 s, tanpa query dari Blade): **Top Kecamatan**, **Top Kelurahan**, **Wilayah dengan Backlog Tertinggi**, dan **Wilayah × Status**. Semua berasal dari kolom administratif `complaints.kecamatan_id` / `complaints.kelurahan_id` (`GROUP BY`; koordinat **tidak** dipakai di sini — dimensi administratif ≠ dimensi koordinat). **Backlog** = laporan **aktif** saja (`submitted` + `in_progress`, sesuai lifecycle LC-2), memakai definisi status tunggal yang sudah berlaku (`ComplaintStatus` / konstanta service). Setiap ranking dibatasi **Top 5** dengan tie-breaker deterministik (nama ASC). Wilayah ber-`id` NULL / master hilang **tidak** dipromosikan menjadi wilayah resmi (tidak ada backfill). Layer 2 (Wilayah × Kategori, tren per wilayah, completion rate per wilayah, dst.) **di luar scope**. **Tanpa** route/migrasi/dependency baru.
- Lampiran disimpan melalui Laravel Storage abstraction, bukan path publik mentah.
- Animasi diterapkan secara konsisten ke seluruh komponen UI yang terlihat dan komponen interaktif, dengan fallback aksesibilitas `prefers-reduced-motion`.
- Tidak memakai React/Node.js API terpisah karena kebutuhan pengguna secara eksplisit memilih Laravel. Tidak memakai Redis, queue server, CDN, object storage eksternal, atau microservices pada MVP kecuali kebutuhan dan infrastruktur telah disetujui.
